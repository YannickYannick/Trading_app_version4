# Configuration Cron - Rafraîchissement des Tokens Saxo
# ========================================================
# Ce fichier contient la configuration cron pour rafraîchir automatiquement
# les tokens OAuth2 des brokers Saxo toutes les 20 minutes.

# IMPORTANT: Sur HostArmada/cPanel, les cron jobs se configurent via l'interface web
# Référence: cPanel > Advanced > Cron Jobs

# ----------------------------------------------------
# CONFIGURATION CRON (via cPanel)
# ----------------------------------------------------

# Minute: */20 (toutes les 20 minutes)
# Hour: * (toutes les heures)
# Day: * (tous les jours)
# Month: * (tous les mois)
# Weekday: * (tous les jours de la semaine)

# Commande complète à entrer dans cPanel (VERSION OPTIMALE - RECOMMANDÉE):
# ----------------------------------------------------

/home/lebaffc1/virtualenv/Trading_app_version4/backend/3.12/bin/python /home/lebaffc1/Trading_app_version4/backend/manage.py refresh_broker_tokens --minutes-before 30 >> /home/lebaffc1/logs/cron_saxo_tokens.log 2>&1

# ----------------------------------------------------
# EXPLICATION DE LA COMMANDE
# ----------------------------------------------------
#
# 1. source /home/lebaffc1/virtualenv/.../activate

#    → Redirige la sortie (stdout + stderr) vers un fichier de log
#    → Permet de débugger en cas de problème

# ----------------------------------------------------
# NOTES IMPORTANTES
# ----------------------------------------------------
#
# 1. SÉCURITÉ DES TOKENS
#    - Les tokens Saxo ont une durée de vie limitée (généralement 20 minutes à 1 heure)
#    - Le refresh_token permet de renouveler l'access_token sans demander à l'utilisateur de se reconnecter
#    - Ne jamais partager ou logger les tokens en clair
#
# 2. FRÉQUENCE DE RAFRAÎCHISSEMENT
#    - 20 minutes est optimal pour Saxo (tokens expirent en ~20-30 min)
#    - Trop fréquent = sollicitation inutile de l'API Saxo
#    - Pas assez fréquent = risque d'expiration et perte de connexion
#
# 3. GESTION DES ERREURS
#    - Si le refresh échoue, l'utilisateur devra se reconnecter manuellement via l'interface
#    - Logs à surveiller pour détecter les échecs répétés
#    - Possibilité d'ajouter des alertes email en cas d'échec
#
# 4. PERFORMANCE
#    - La commande est rapide (<5 secondes pour quelques comptes)
#    - Pas d'impact sur les performances du serveur
#    - Utilise le BrokerService existant (optimisé)
